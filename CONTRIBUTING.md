# Как устроены и проверяются скиллы

Правила для авторов изменений: и для людей, и для AI-агентов, которые правят этот репозиторий.

## Цикл обновления

Скиллы обновляются раз в месяц, после релиза документации [bitrix-tools/framework-docs](https://github.com/bitrix-tools/framework-docs):

1. Дифф документации с прошлого синка (`whats-new.md` и изменённые страницы).
2. Разборы обновлений ядра за месяц (что сломалось, что появилось).
3. Issue и PR сообщества.
4. Сверка каждого факта и каждого примера с кодом свежего ядра.
5. `php tools/verify-skills.php --kernel=<path>/bitrix/modules` — без ошибок.
6. Семантическое ревью: скрипт ловит несуществующие символы, но не неверное поведение. По каждому изменённому скиллу выбираются самые рискованные утверждения (поведение, значения по умолчанию, `Since`, безопасность, примеры) и перепроверяются по коду ядра.
7. Запись в [CHANGELOG.md](CHANGELOG.md), версия проверки в README и `bitrix-framework`.

Документация — повод для правки, но не источник истины. Если дока и ядро расходятся, прав код ядра; расхождение стоит отметить в скилле одной строкой.

## Формат скилла

Скиллы пишутся на английском: так они короче в токенах, и модели следуют им точнее. README и CONTRIBUTING написаны по-русски для людей.

```
skills/<name>/
├── SKILL.md          # точка входа, всегда загружается при срабатывании
└── rules/*.md        # детали, агент открывает только нужный файл
```

### Frontmatter

```yaml
---
name: bitrix-orm            # совпадает с именем каталога
description: 'D7 ORM tablets, Query/filters, Objectify, batch writes. Use when designing entities, reading or persisting data via DataManager.'
---
```

- `description` загружается в каждую сессию, где установлен набор, поэтому она не длиннее **250 символов**. Схема: «что это (ключевые классы). Use when … (триггеры)».
- Никаких «Covers…», «Applied when…», «Key terms —». Ключевые слова вписываются в само предложение.
- `description` всегда в одинарных кавычках. Без кавычек `: ` ломает YAML, и `npx skills` молча пропускает скилл, а ` #` обрезает описание как комментарий. В двойных кавычках `\` — escape-символ, а в описаниях есть `Engine\Controller`. Апостроф внутри удваивается: `''`.

### Размеры

| Файл | Бюджет |
| --- | --- |
| `SKILL.md` без `rules/` | до 6 КБ |
| `SKILL.md`-роутер | до 2,5 КБ |
| `rules/<topic>.md` | до 6 КБ, одна тема |

Если скилл перерос 6 КБ, его режут на роутер и `rules/`.

### Роутер

```markdown
# Bitrix ORM

Baseline: main 23.0+ · Verified: main 26.800.0

| Task | Read |
| --- | --- |
| Tablet, fields, relations | `rules/tablet-map.md` |
| Queries, filters, collections | `rules/reading.md` |

## Invariants
- 3–7 правил, которые действуют всегда, независимо от rules-файла.
```

Без абзацев «How to use» и «Progressive disclosure»: таблица и так говорит, что открывать.

### Версии

- Строка `Baseline: main 23.0+ · Verified: main X.Y.Z` в начале каждого `SKILL.md`. Для модулей, отличных от main, указывается версия модуля (`Verified: documentgenerator 26.200.0, main 26.800.0`).
- Скиллы `bitrix24-*` вместо baseline пишут, где они применимы: `Scope: Bitrix24 on-premise · Verified: crm 26.800.0, main 26.800.0` или `Scope: Bitrix24 cloud + on-premise · Verified: …`.
- Всё, чего нет в baseline, помечается `**Since main X.Y**`.
- Если точная версия неизвестна, пишется самая ранняя проверенная версия со звёздочкой: `**Since main 26.250\***` (есть в 26.250.100, нет в 25.100.500). Легенда звёздочки — в `bitrix-framework`.
- Для каждого `Since` один fallback: как сделать то же на старом ядре.
- Модули, которых нет в эталонных старых ядрах (`crm`, `tasks`, `im`, `intranet`, `bizproc` …), получают `Since` только по точной версии из разбора обновления (дифф версии модуля). Без такого разбора пометки нет, а скилл даёт проверку в коде (`class_exists(...)`) и путь для старой версии.

### Код

- Каждый класс, метод, константа и именованный аргумент в примере существуют в ядре указанной версии. Не существующих API не бывает «для иллюстрации».
- Примеры короткие: только то, что иллюстрирует правило. `declare(strict_types=1)` и `use` — только в примерах целых файлов.
- Именованные аргументы ядра не используются, если имя параметра не проверено (сигнатуры ядра меняются без предупреждения).
- Опасные операции (удаление, `down` без аргументов, `force`) помечаются прямо в примере.

### Содержание

- Скилл пишет, **как правильно** в `/local/`, а не пересказывает документацию.
- Нет ссылок на `AGENTS.md`: при установке через `npx skills` его нет. Общие каноны живут в скилле `bitrix-framework`, остальные ссылаются на него или на профильный скилл по имени.
- Одно правило — одно место. Таблица DI, `/local/`, CSRF и т. п. не дублируются в каждом скилле.
- Чеклист в конце — до 6 пунктов, каждый проверяемый.

## Проверка

```bash
php tools/verify-skills.php --kernel=/path/to/bitrix/modules          # все скиллы
php tools/verify-skills.php --kernel=/path/to/bitrix/modules bitrix-orm
```

Скрипт:

- прогоняет `php -l` по каждому PHP-блоку (фрагменты оборачиваются в класс или функцию);
- находит в примерах FQCN, `use`-импорты и статические вызовы и сверяет классы, методы и константы с индексом, построенным по исходникам ядра;
- проверяет frontmatter, длину `description`, бюджеты размеров, ссылки на `rules/*.md` и на другие скиллы.

Нужен индекс ядра Битрикс24 (коробки), чтобы проверялись и модули `crm`, `tasks`, `im` и т. п.

## Pull request

- Одна тема — один PR. В описании: какой скилл, что было неверно, путь к файлу ядра со строкой.
- Проверка `tools/verify-skills.php` проходит.
- Запись в `CHANGELOG.md` в разделе `Unreleased`.
