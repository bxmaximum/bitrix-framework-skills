# Как устроены и проверяются скиллы

Правила для авторов изменений: и для людей, и для AI-агентов, которые правят этот репозиторий.

## Цикл обновления

Скиллы обновляются раз в месяц, после релиза документации [bitrix-tools/framework-docs](https://github.com/bitrix-tools/framework-docs):

1. Дифф `framework-docs` и [REST-документации Битрикс24](https://github.com/bitrix24/b24restdocs) с прошлого синка (`whats-new.md` и изменённые страницы). Зафиксировать исходный и новый коммиты.
2. Разборы обновлений ядра за месяц (что сломалось, что появилось).
3. Issue и PR сообщества.
4. Сверка новых и изменённых утверждений и примеров с кодом свежего ядра. Для облачных REST-методов — с официальной страницей метода; наличие на коробке проверяется отдельно. Сохранить версии модулей и пути к коду, подтверждающие рискованные изменения.
5. `php tools/verify-skills.php --kernel=<path>/bitrix/modules` — без ошибок.
6. Семантическое ревью: скрипт ловит несуществующие символы, но не неверное поведение. По каждому изменённому скиллу выбираются самые рискованные утверждения (поведение, значения по умолчанию, `Since`, безопасность, примеры) и перепроверяются по коду ядра.
7. Запись в [CHANGELOG.md](CHANGELOG.md), версия проверки в README и `bitrix-framework`. Не повышать `Verified` автоматически: она относится к реально проверенному источнику.

Документация — повод для правки, но не источник истины. Если дока и ядро расходятся, прав код ядра; расхождение стоит отметить в скилле одной строкой.

## Формат скилла

Инструкции, описания, заголовки и пояснения примеров пишутся на русском для сообщества BXMax. Имена скиллов, API, пути, идентификаторы, коды ошибок и машинные метки `Baseline`, `Scope`, `Verified`, `Since` сохраняются. Поддерживается одна языковая версия. К агенту обращаемся на «ты» в повелительном наклонении («проверь», «используй»); «вы» остаётся только в строках интерфейса для конечных пользователей.

```
skills/<name>/
├── SKILL.md          # точка входа, всегда загружается при срабатывании
└── rules/*.md        # детали, агент открывает только нужный файл
```

### Frontmatter

```yaml
---
name: bitrix-orm            # совпадает с именем каталога
description: 'Используй для D7 ORM Битрикса: DataManager, query(), объекты и коллекции, связи и пакетная запись. SQL без ORM — bitrix-database.'
---
```

- Агент использует `name` и `description` для выбора скилла. Локальный предел описания — **250 символов**, обычно достаточно 150–200. Сначала задача и среда, затем 2–4 ключевых класса или метода, по которым агент узнает вставленный пользователем код (`CIBlockElement`, `TaggedCache`, `Mail\Event::send`), и при необходимости граница с соседним скиллом. Описание без единого имени API допустимо только у канона `bitrix-framework`.
- Не перечислять весь каталог методов в описании: подробности находятся в таблице тем. Не добавлять ключевые слова, привлекающие чужие задачи.
- `description` всегда в одинарных кавычках. Без кавычек `: ` ломает YAML, и `npx skills` молча пропускает скилл, а ` #` обрезает описание как комментарий. В двойных кавычках `\` — escape-символ, а в описаниях есть `Engine\Controller`. Апостроф внутри удваивается: `''`.

### Размеры

| Файл | Бюджет Unicode-символов |
| --- | --- |
| `SKILL.md` без `rules/` | до 6000 |
| `SKILL.md`-роутер | до 2500 |
| `rules/<topic>.md` | до 6000, одна тема |

Это ориентиры для читаемости, не оценка токенов. Разбивать файл стоит по самостоятельным задачам: нужная тема должна читаться без остальных. Короткому цельному скиллу дополнительный роутер не нужен.

### Роутер

```markdown
# Bitrix ORM

Baseline: main 23.0+ · Verified: main 26.1000.0

Перед PHP-кодом прочитай `bitrix-framework`, если ещё не читал его в этой задаче.

| Задача | Прочитай |
| --- | --- |
| Сущность, поля, связи | `rules/tablet-map.md` |
| Запросы, фильтры | `rules/reading.md` |

## Основные правила
- 3–7 правил, которые действуют всегда, независимо от rules-файла.
```

Таблица должна связывать задачу с конкретным файлом. Пути `rules/` относительны каталогу скилла. Читать все темы подряд не требуется. Общий канон открывается один раз на задачу; его не надо копировать во все входы.

### Версии

- Строка `Baseline: main 23.0+ · Verified: main X.Y.Z` в начале каждого `SKILL.md`. Для модулей, отличных от main, указывается проверенная версия модуля (`Verified: documentgenerator 26.400.0, main 26.1000.0`).
- Скиллы `bitrix24-*` вместо baseline могут указывать область: `Scope: Bitrix24 on-premise · Verified: crm 26.1900.0, main 26.1000.0` или `Scope: Bitrix24 cloud + on-premise · Verified: …`.
- Всё, чего нет в baseline, помечается `**Since main X.Y**`.
- Если точная версия неизвестна, пишется самая ранняя проверенная версия со звёздочкой: `**Since main 26.250\***` (есть в 26.250.100, нет в 25.100.500). Легенда звёздочки — в `bitrix-framework`.
- Для каждого `Since` один fallback: как сделать то же на старом ядре.
- Модули, которых нет в эталонных старых ядрах (`crm`, `tasks`, `im`, `intranet`, `bizproc` …), получают `Since` только по точной версии из разбора обновления (дифф версии модуля). Без такого разбора пометки нет, а скилл даёт проверку в коде (`class_exists(...)`) и путь для старой версии.

### Код

- Каждый класс, метод, константа и именованный аргумент в примере существуют в ядре указанной версии. Не существующих API не бывает «для иллюстрации».
- Примеры короткие: только то, что иллюстрирует правило. `declare(strict_types=1)` и `use` — только в примерах целых файлов.
- Именованные аргументы ядра не используются, если имя параметра не проверено (сигнатуры ядра меняются без предупреждения).
- Опасные операции (удаление, `down` без аргументов, `force`) помечаются прямо в примере.

### Содержание

- Скилл пишет, **как правильно** в `/local/`, а не пересказывает документацию.
- Нет ссылок на `AGENTS.md`: при установке через `npx skills` его нет. Общие каноны живут в скилле `bitrix-framework`, остальные ссылаются на него или на профильный скилл по имени.
- Одно правило — одно место. Таблица DI, `/local/`, CSRF и т. п. не дублируются в каждом скилле.
- Чеклист в конце — до 6 пунктов с Markdown checkbox (`- [ ]`), каждый проверяемый.
- Скилл не расширяет задачу: исправление кеша не требует замены инфраструктуры, проверка REST-метода не требует настройки MCP, облачный REST не требует чтения PHP-ядра.
- Если инструмент недоступен, дать доступный способ проверки и конечный критерий остановки. Не требовать бесконечных повторов и не выдумывать API.

## Проверка

```bash
php tools/verify-skills.php --kernel=/path/to/bitrix/modules          # все скиллы
php tools/verify-skills.php --kernel=/path/to/bitrix/modules bitrix-orm
php tools/verify-skills.php --files-only                              # структура и PHP-синтаксис, без API
php tools/test-verify-skills.php                                      # только при правке самого verify-skills.php
```

Скрипт:

- прогоняет `php -l` по каждому PHP-блоку (фрагменты оборачиваются в класс или функцию);
- находит в примерах FQCN, `use`-импорты и статические вызовы и сверяет классы, методы и константы с индексом, построенным по исходникам ядра;
- проверяет frontmatter, длину `description`, бюджеты размеров, ссылки на `rules/*.md` и на другие скиллы.

Нужен индекс ядра Битрикс24 (коробки), чтобы проверялись и модули `crm`, `tasks`, `im` и т. п. Модуля `sprint.migration` в коробке нет: его каталог передаётся вторым `--kernel=<path>/bitrix/modules/sprint.migration`.

Заведомо несуществующий или удалённый API в пояснении помечается на той же строке `<!-- verify:negative -->`: ошибка символа в inline-примере станет предупреждением. Пример должен явно объяснять, что так делать нельзя. Язык фразы на результат проверки не влияет; PHP-блоки аннотация не ослабляет. Не помечать ею рабочие примеры ради зелёного отчёта.

Режим `--files-only` не проверяет символы и совместимость с ядром; это явно указано в выводе. Он удобен при переводе и правке структуры, но не заменяет полную проверку перед обновлением `Verified`.

## Pull request

- Одна тема — один PR. В описании: какой скилл, что было неверно, путь к файлу ядра со строкой.
- Проверка `tools/verify-skills.php` проходит.
- Запись в `CHANGELOG.md` в разделе `Unreleased`.
