# REST 3.0 methods

**Since rest 26.200\***. Fallback: Engine controller + `restIntegration` (`rules/classic.md`); both paths work side by side. Calling v3 (URL, body, batch, `Idempotency-Key` header): `bitrix24-rest-api` `rules/rest-v3.md`.

## Registration

Module `.settings.php` (the module must be installed):

```php
return [
    'rest' => [
        'value' => [
            'defaultNamespace' => '\\Vendor\\Shop\\Infrastructure\\Rest\\Controller', // required
            // 'namespaces' => ['\\Vendor\\Shop\\Rest\\Old'], // more roots
            // 'routes' => ['alias' => 'vendor.shop.order.list'],
        ],
        'readonly' => true,
    ],
];
```

- Other keys: `controllerProvider` (subclass of `Bitrix\Rest\V3\Schema\SchemaProvider`), `documentation`. Kernel samples: `rest/.settings.php`, `main/.settings.php`.
- Every class under those namespaces that extends `Bitrix\Rest\V3\Controller\RestController` is a controller. Every public `*Action` whose return type extends `Bitrix\Rest\V3\Interaction\Response\Response` is a method.
- Method name = `<moduleId>.<class path below the namespace, lowercased, \ → .>.<action>`: `…\Controller\Order::listAction` in `vendor.shop` → `vendor.shop.order.list`. To move controllers, set a new `defaultNamespace` and keep the old one in `namespaces`.
- Scopes of a method: every dot-prefix of its name (`vendor`, `vendor.shop`, `vendor.shop.order`, …) plus `#[Scope('x')]` values on the action; any one of them is enough.
- Discovery is cached per module version + mtime of `install/version.php`. A new action gives `MethodNotFound` until you touch `install/version.php` or call `\Bitrix\Rest\V3\CacheManager::cleanAll()`. Dev only: global `.settings.php` `'rest' => ['value' => ['v3_cache_disabled' => true]]`.

## ORM-backed controller

```php
namespace Vendor\Shop\Infrastructure\Rest\Dto;

use Bitrix\Rest\V3\Attribute\Filterable;
use Bitrix\Rest\V3\Attribute\OrmEntity;
use Bitrix\Rest\V3\Attribute\ResolvedBy;
use Bitrix\Rest\V3\Attribute\Sortable;
use Bitrix\Rest\V3\Dto\Dto;
use Vendor\Shop\Infrastructure\Rest\Controller\Order;
use Vendor\Shop\Model\OrderTable;

#[OrmEntity(OrderTable::class)]
#[ResolvedBy(Order::class)]
final class OrderDto extends Dto
{
    #[Filterable, Sortable]
    public ?int $id;

    #[Filterable]
    public ?string $statusId; // ↔ ORM field STATUS_ID
}
```

```php
namespace Vendor\Shop\Infrastructure\Rest\Controller;

use Bitrix\Rest\V3\Attribute\DtoType;
use Bitrix\Rest\V3\Controller\GetOrmActionTrait;
use Bitrix\Rest\V3\Controller\ListOrmActionTrait;
use Bitrix\Rest\V3\Controller\RestController;
use Vendor\Shop\Infrastructure\Rest\Dto\OrderDto;

#[DtoType(OrderDto::class)]
final class Order extends RestController
{
    use ListOrmActionTrait; // vendor.shop.order.list
    use GetOrmActionTrait;  // vendor.shop.order.get
}
```

- Traits: `List|Get|Add|Update|Delete|Tail|AggregateOrmActionTrait`. Canonical kernel pair: `main/lib/Rest/V3/Controller/EventLog.php` + `main/lib/Rest/V3/Dto/EventLogDto.php`.
- Property attributes: `Filterable`, `Sortable`, `Editable`, `Required`, `Title`, `Description`, plus main `Validation\Rule\*` (`bitrix-validation`).
- **Since rest 26.600** a list without `select` reads only the DTO's scalar fields (was `*`); code must not rely on other columns.
- Trait actions are `final` and don't filter rows by rights: guard with a prefilter (`...parent::getDefaultPreFilters()`, then yours; see `EventLog`) or write your own action.

## Custom action

```php
use Bitrix\Main\Validation\Rule\PositiveNumber;
use Bitrix\Rest\V3\Interaction\Request\Request;

final class CancelRequest extends Request
{
    #[PositiveNumber]
    public int $orderId;
}
```

```php
#[\Bitrix\Rest\V3\Attribute\Scope('vendor.shop.write')]
#[\Bitrix\Rest\V3\Attribute\NotIdempotent]
public function cancelAction(CancelRequest $request): \Bitrix\Rest\V3\Interaction\Response\UpdateResponse
{
    if (!$this->canCancel($request->orderId)) {
        throw new \Bitrix\Rest\V3\Exception\AccessDeniedException();
    }
    \Bitrix\Main\DI\ServiceLocator::getInstance()->get(OrderService::class)->cancel($request->orderId);

    return new \Bitrix\Rest\V3\Interaction\Response\UpdateResponse();
}
```

- The `Request` subclass is filled from the JSON body; a controller without `#[DtoType]` fails with `ClassRequireAttributeException`. No constructor DI (`bitrix-framework`).
- Overridden `getDefaultPreFilters()` / `getDefaultPostFilters()` must spread `parent::`: it carries the idempotency filter (**Since rest 26.600**).
- Don't redeclare `$responseLanguage` / `getResponseLanguage()` (typed since 26.600, Fatal).

## Errors

- Throw `Bitrix\Rest\V3\Exception\*` (`AccessDeniedException`, `EntityNotFoundException($id)`, …). The error code is the exception FQCN with `\` → `_`, upper-cased; the HTTP status comes from the class. Any other exception becomes `InternalException` (500) and is logged.
- Own error: extend `RestException`, implement `getMessagePhraseCode()`, optionally `protected const STATUS = '409 Conflict'`; the phrase lives in the class's lang file. Add `SkipWriteToLogException` for expected errors.

## Idempotency, enums, batch (**Since rest 26.600**)

- Actions taking `AddRequest`/`UpdateRequest`/`DeleteRequest` honour the `Idempotency-Key` header automatically. Opt in others with `#[Idempotent(ttl: 3600)]`, opt out with `#[NotIdempotent]` (wins). Only 200 responses are stored; if storage fails the action runs unguarded.
- `#[DynamicEnum(Provider::class)]` on a DTO property: provider implements `Bitrix\Rest\V3\Dto\DynamicEnum\DynamicEnumProvider` (`getType()`, `getValues()`), built with `new` (no constructor args). After data changes call `DynamicEnumRegistry::clear(Provider::class)`.
- `rest.deferredbatch.*` runs through the Messenger queue `rest.deferred_batch`: consumers must run (`bitrix-background-jobs`). Lists inside a deferred batch stay paginated (26.650 bug).
- Don't use `#[Enabled(...)]` on controllers: in rest 26.650 its constructor throws for any provider (`!$provider instanceof …` on a string).
